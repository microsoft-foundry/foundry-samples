# Coding Agent Instructions — Voice Conversation Engine LangGraph Python

This is a Microsoft Foundry hosted conversation engine that implements Voice Live Bridge Protocol
`1.0` over `voice_conversation_engine`. Voice Live owns the audio pipeline; this sample handles
only typed text and control events. Preserve the existing repository paths and resource identifiers.

## Deployment mode

- Direct code deployment: `azure.yaml` declares Python 3.13 and `main.py` as the entry point.
- Keep the sample self-contained under this directory. Do not add sibling-path dependencies,
  private package feeds, local wheels, or generated `.vscode` files.

## Key files

- `azure.yaml` — Foundry project, model, hosted-agent metadata, and protocol declaration
- `src/voice-live-bridge-langgraph-python/main.py` — server entry point
- `src/voice-live-bridge-langgraph-python/voice_runtime.py` — thin Bridge callbacks and command dispatch
- `src/voice-live-bridge-langgraph-python/response_coordinator.py` — response execution, terminal
  sequencing, cancellation, and detached-task cleanup
- `src/voice-live-bridge-langgraph-python/state.py` — bounded connection state and session store
- `src/voice-live-bridge-langgraph-python/model_contract.py` — model backend protocol shared without
  circular imports
- `src/voice-live-bridge-langgraph-python/langgraph_agent.py` — explicit StateGraph tool loop and Foundry Responses adapter
- `src/voice-live-bridge-langgraph-python/pyproject.toml` — runtime and development dependencies
- `src/voice-live-bridge-langgraph-python/uv.lock` — fully pinned dependency graph
- `sample.yaml` — repository build-readiness validation

Do not commit `.vscode` launch or task files generated by the Foundry Toolkit.

## Dependency workflow

Follow `samples/python/hosted-agents/DEPENDENCY_POLICY.md`. Runtime and development
dependencies are declared in `pyproject.toml`; `uv.lock` is the portable, fully
pinned consumer artifact. Regenerate the lock whenever a dependency input changes,
and run the static and resolver-backed policy checks before completing dependency
changes.

## Runtime logging

Use the standard `logging` module for server diagnostics. Reserve `print()` for local CLI utilities
such as the smoke client, where stdout is the intended interface. Never log prompts, responses,
credentials, or bearer tokens.

## Development workflow

From an initialized agent project, use `azd provision`, `azd ai agent run`, and `azd deploy` for the
hosted-agent lifecycle. Do not use `azd ai agent invoke` for this sample because it does not produce
Voice Live Bridge WebSocket events; use `scripts/smoke_test.py` for the local protocol check.

## Protocol constraints

- Declare `voice_conversation_engine:1.0.0` and use `/voice_conversation_engine`; neither legacy
  Bridge metadata key is required. Keep the message handshake at Bridge Protocol `1.0`.
- Use `UserBargeIn` / `on_user_barge_in` for `user.barge_in`, preserving heard-text reconciliation.
- Preserve the original model/tool backend and lifecycle; this is a protocol adaptation, not a
  replacement runtime. The SDK's independent `/invocations_ws` route remains available.
- Confirm matching Hosted ingress and Voice Live support before deployment; local tests alone
  do not prove cloud or managed-audio readiness.
- The application explicitly sends `session.ready` or `session.rejected` and owns response IDs,
  background tasks, cancellation, and conversation state.
- Keep this sample text-only. Protocol `1.0` does not include DTMF, image input, app-driven
  history mutation, or hosted-agent handoff.
